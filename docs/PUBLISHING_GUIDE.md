# 发版操作指南

适用对象：项目维护者。核对日期：2026-09-15。本文把当前流程整理成操作顺序；所有可执行命令及平台变更步骤统一放在 [DEV_WORKFLOW：日常维护与发版入口](../DEV_WORKFLOW.md#日常维护与发版入口)。最新上线身份看 [README](../README.md#当前状态)，下面的示例不能代替下一次发版前的现场核查。

## 先知道网站是怎样更新的

文章、图片与页面代码保存在本机项目里，经检查后构建成静态文件，再上传到 Vercel。Cloudflare 只承接 RUM 性能测量与定时维护，不存文章，也不负责发布网页。网站上线后不需要工作电脑一直开着。

```text
本地修改 → 检查 → Git 提交 → 从干净提交构建并冻结
        → 上传受保护候选 → 检查候选 → 提升到正式域名 → 上线核验
```

三个容易混淆的动作：

| 动作 | 实际作用 |
| --- | --- |
| Git 提交 | 在本机保存一个可追溯版本，不会自动上线 |
| Git 推送 | 把提交送到远端仓库；当前没有接通 Git 自动部署 |
| Vercel 发布 | 把已验收的静态文件交给正式域名，读者才会看到变化 |

当前没有通用的“一键发布”命令，也没有文章管理后台。你可以按本文完成编辑、检查和候选验收；**新发布包及上传会话目前仍需要按本次提交准备**。旧 `.local/` 脚本绑定旧文件、摘要、部署和操作记录，不能直接复制执行。这是现有工具的限制，不是每次都要重新注册账户。

## 一次正常发版，按这个顺序走

### 1. 列清楚这次要发什么

写下涉及的文章、图片或页面，确认工作区已有修改分别属于哪次工作。只改操作文档、没有改变网站内容和配置时，不需要部署网站。

新文章先走 [文章流程](ARTICLE_WORKFLOW.md)。若修改域名、统计开关、RUM 窗口、表单或数据库，则属于额外运行变更，需要独立核对影响；不要混进普通文章发布。

### 2. 在本地检查和预览

按 DEV_WORKFLOW 的 [环境准备](../DEV_WORKFLOW.md#日常步骤-a环境准备) 和 [本地检查](../DEV_WORKFLOW.md#日常步骤-b本地检查与两种构建) 操作。有错误就先处理错误，再继续。

| 输出目录 | 作用 | 能否上传 |
| --- | --- | --- |
| `dist/` | review 审稿站，带 noindex、零客户端 JS | 不能 |
| `.local/public-build/` | 显式正式 origin 生成的 public 静态文件 | 通过检查、绑定干净源并冻结后，才可作为发布输入 |
| `.local/` 内某次冻结目录 | 保存该次不可变文件与摘要的发布包 | 仅限对应已验收版本 |

本地审稿看正文、图片、导航和手机排版；正式候选还要核对真实托管、SEO 与脚本。review 通过不等于 public 通过，构建成功也不等于已经部署。

### 3. 提交并固定版本

按 [精确提交入口](../DEV_WORKFLOW.md#日常步骤-c保存本地版本) 逐个列出要提交的文件。记下完整提交 SHA；提交后工作区必须干净，才能生成正式发布包。不要用“全部暂存”顺带带入不相关修改，也不要为得到干净状态删除已有工作。

提交前的检查用于发现问题；正式发布证据必须绑定提交后的干净源。若先前是在未提交修改上构建，提交后应重走检查与 public/review 构建。正式包冻结后改了文件，就需要重新核定版本和受影响验证，不能只改包里的提交号。

### 4. 准备本次发布包与上传会话

这是当前需要工程准备的一步，详细输入和顺序见 [发布执行门禁](../DEV_WORKFLOW.md#日常步骤-d冻结上传与正式发布)。你应拿到：

- 本次源 SHA、锁文件摘要、检查结果和 public origin。
- 所有待上传文件的路径、字节数与 SHA256，以及冻结包摘要。
- 本次上传请求、唯一操作标识、受保护候选的验收方式。
- 当前正式部署 ID，作为本次故障时的回退目标。

2026-09-15 的 `.local/rum-release-73e482a/` 与 `.local/rum-deployment-73e482a/` 是一次成功记录；它们不是下一篇文章的发布包。`.local/` 不进 Git，换电脑或清理目录后不会随源码自动恢复。

可把下面这段交给协助发版的人：

> 请在现有项目目录核对本次变更，按 DEV_WORKFLOW 从通过检查的干净提交准备新的冻结包和受保护上传会话。列出源 SHA、文件清单、验证结果、目标项目及当前回退部署，准备到可审阅状态。不要复用旧 attempt，不复制旧验收结果；准备好后再由我确认本次上传与正式提升。

### 5. 候选验收通过后，再正式提升

先核对 Vercel 团队和项目，再使用本次会话上传。若需要 Token，等包和本地输入入口准备好后再创建短期凭据；在页面实际提供的权限范围内选择最小范围。凭据只输入本地掩码入口，不写进聊天、Markdown、Git 或命令行参数。

候选必须 READY，并确认匿名访问受到预期保护。登录后检查：

- 首页、改动的文章、所属合集和 Related 链接都能打开。
- 桌面与手机宽度下正文可读，图片无破损、裁切合理，没有横向溢出。
- 来源链接、Content note、图片说明、日期正确；正文和导航在关闭 JS 后仍可使用。
- canonical 指向正式网站；Sitemap/RSS/robots 与本次公开页面一致。
- Newsletter 和 Reader Request 保持未开放；没有意外加入脚本或表单。

候选通过后按 DEV_WORKFLOW 提升**同一份已验收部署**。不要把相邻旧部署当作候选，也不要使用会重新构建的 Redeploy 代替本次提升。Vercel 区分普通 Preview 与 staged production；本项目当前使用后者。参见 [Vercel Promoting Deployments](https://vercel.com/docs/deployments/promoting-a-deployment)，访问于 2026-09-15。

### 6. 上线后确认读者实际拿到新版

发布完成以正式域名回查为准：部署 ID 正确，全部公开文件的 HTTP 状态、MIME、长度和 SHA256 与冻结清单一致，浏览器能读到新内容。

人工自查看 [退出统计的首页](https://mythic-china-beta.vercel.app/?analytics=off&rum=off)。检查其他页面时也给该页 URL 加上 `?analytics=off&rum=off`；站内跳转不保证保留这些参数。此模式用于阅读 QA，不能证明真实统计收数正常。

记录发布的提交、部署 ID、时间、核验结论及未验项目；关闭临时本地服务并清理凭据会话。状态文档若在冻结后更新，需要另行提交，不能反过来改写原冻结包的身份。

## 出问题时怎么处理

| 现象 | 先做什么 |
| --- | --- |
| 本地检查失败 | 读第一条具体错误，修正内容或对应验收清单；不跳过检查强行上传 |
| 新文章未出现 | 核对内容状态、正式包版本，以及新增页面/图片是否进入独立验收清单 |
| 候选还是旧内容 | 核对部署 ID 与源 SHA，不靠反复点 Redeploy 猜测 |
| 上传超时、结果未知 | 先按本次操作标识查询是否已创建，不重复上传 |
| Token 过期或 403 | 核对身份、权限与操作结果，恢复身份后继续同一流程；不要换项目或扩大权限试错 |
| 正式站严重影响阅读 | 按 DEV_WORKFLOW 的 [回退入口](../DEV_WORKFLOW.md#日常步骤-e故障回退) 恢复本次记录的上一个正常生产部署 |

Vercel 回退的是网站部署，不会回退本地文件或 Cloudflare D1 数据。当前 Hobby 计划的 Instant Rollback 只支持紧邻的上一份部署，操作时以页面列出的合格目标为准。参见 [Vercel Instant Rollback](https://vercel.com/docs/instant-rollback)，访问于 2026-09-15。

## Cloudflare 哪些需要日常关注

普通文章发布沿用现有接收服务。不要每发一篇就重建数据库、粘贴 Worker 代码或重开观察窗。

2026-09-15 上线回执：`RUM_ENABLED=true`，DB 绑定为 `mythic-china-rum-db`，Cron 为 `0 * * * *`，Logs/Traces 主开关关闭。当前固定观察期是北京时间 **2026-09-16 08:00 至 2026-09-30 08:00**，结束时刻不计入窗口；它不是永远滚动的“最近 14 天”。换窗需要客户端配置、Privacy、服务端记录和验收共同一致。

零样本不一定是调度坏了：先看窗口是否开始，再看真实流量与隐私退出情况；Cron Success 和 maintenance 推进证明维护任务运行，不能证明浏览器已经送来测量。OPTIONS 204 也只证明预检通道。不要为了看到非零而反复刷新或发送假数据。

Cloudflare Cron 使用 UTC，变更可能需要最多约 15 分钟传播。参见 [Cloudflare Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)，访问于 2026-09-15。当前完整观察、真人阅读和真机验收仍按 [011](requirements/011-public-beta-validation.md) / [017](requirements/017-real-user-monitoring.md) 进行。
